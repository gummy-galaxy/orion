# Pull requests

When a pull request changes what the app shows, attach before and after screenshots to its description, or videos when the change is an interaction, an animation, or takes several steps to reach. Follow `.claude/skills/pr-screenshots/SKILL.md`, which captures or records both sides the same way, headless, into a scratch folder, uploads them to GitHub through the comment box without posting, and writes the description with `gh`.

CI's perf workflow compares every pull request that touches `workspace/orion-app/` against its base branch and keeps the report in one pull request comment, replaced on each run. It skips drafts and runs once a pull request is ready for review. It also runs on every push to `main`, and each run records its medians in PostHog so performance can be charted over time. When a pull request touches canvas rendering, CSS animations or effects, `derive`, `layout`, `merge`, `snap`, the Jotai state, or `Canvas.tsx`, read that comment once it posts. Summarize any flagged regressions in the pull request's Testing section, or say why a flagged change is acceptable. To check before pushing, run `npm run perf` from `workspace/orion-app/`. It takes several minutes and measures this machine, so run one at a time with no other heavy work going.

A pull request that finishes an issue closes it. Put `Closes #<n>` in the description, so merging it closes the issue. Don't point at an issue with "Part of", "Advances", "Related", or any other label instead. When a pull request finishes only some of an issue, say in its description which items on the issue's Progress checklist it finishes. When it leaves concrete work undone, add that work to the checklist, or file it as one follow-up issue when it stands on its own.

Give each pull request a place on the canvas. When a card already tracks the work, attach the pull request to it with `orion card set <id> --ref https://github.com/gummy-galaxy/orion/pull/<n>`. Otherwise add a card for it in the outcome group it belongs to.
