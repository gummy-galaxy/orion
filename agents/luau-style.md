# Luau style

- Put a CLI module in the layer folder of `workspace/orion-cli/src` whose job it shares, as that package's README lays out, and require only from its own layer or below. Keep types, constants, and config tables at the top of `src`, and code that only `.lute` scripts use in `.lute/lib`.
- Export one function per module, from a file named after it with a verb first, such as `common/platform/getDataDir.luau`. Put shared types in a sibling `types.luau` and tests in `<function>.spec.luau` beside it. Constant tables, data lists, and command modules stay tables.
- A module that builds an object, such as the server's sync loop, exports one `create` function named for what it makes, like `server/createSyncLoop.luau`, rather than a table holding `create`. Its constants go in a `constants.luau` and its shared types in a `types.luau` beside it.
- End a function's name in `Async` when it waits on a `CommandRunner`, either by calling one or by calling a function that does, such as `sources/github/api/fetchRepositoriesAsync.luau`. The suffix spreads to callers, table fields like an adapter's `collectAsync` included, so a caller can tell which calls might belong in a `task.spawn`. It stops at callbacks whose name a shared shape sets, such as a command's `run`, and skips the quick process probes `isProcessAlive` and `getParentPid`.
- Keep a helper that only one module uses as a local function there. Once a second module needs it, move it into its own module rather than copying it. Look for an existing helper, such as `getStringField`, before writing one.
- Keep related requires, type aliases, constants, and short assignments together. Separate those groups and adjacent functions with blank lines.
- Name a required module after the module itself, such as `local cli = require("@batteries/cli")` and `local io = require("@lute/io")`, without prefixing the package.
- Within functions, use blank lines between logical steps: setup, guards, loops and branches, state changes, and the final result. Keep statements that form one step together.
- Run StyLua after editing Luau, then review the spacing yourself. StyLua sorts requires and formats statements, but does not add these logical blank lines.
- Keep comments within 80 columns, counting a tab as four, while code stays at StyLua's 120. The `comment_width` lint flags longer ones, and `lute lint --auto-fix <paths>` from `workspace/orion-cli` rewraps them. Move a long comment that follows code onto its own line above it.
- StyLua never splits a string, so the `string_width` lint flags any line holding one past 120 columns. Split it by hand: join pieces with `..` across lines, breaking at a sentence or a comma, or put the lines in a table and `table.concat` them. Whitespace inside a multi-line JSON fixture is free to rewrap instead.
- Keep `.lute/` to a few top-level scripts, each either a category of related jobs, such as `build`, `install`, or `report`, or a job that stands on its own, such as `mutate`. Add a new job, especially platform- or CI-only glue, as a subcommand of the category it fits, like `lute run install sqlite`, rather than as its own script. A category stays one file while its subcommands are short. Once they grow long, it becomes a folder whose `init.luau` dispatches on `process.args[2]` and requires one module per subcommand with `@self/<module>`, each exporting one function and doing nothing until it's called. Don't put a file and a folder of the same name side by side, such as `report.luau` beside `report/`, since requires into the folder become ambiguous.
- `lute run analyze` checks formatting, types, and that the files `lute run generate` writes are current, which needs `npm ci` in `docs/` first. It lints with Lute's built-in rules plus Orion's own in `.lute/lints`, one folder per rule with an `init.luau` and its `init.spec.luau`, which `lute test workspace/orion-cli .lute` runs from the repository root. Add a rule there rather than reaching for another linter, and silence one spot with a `-- lute-lint-ignore(<rule>)` comment above it.
